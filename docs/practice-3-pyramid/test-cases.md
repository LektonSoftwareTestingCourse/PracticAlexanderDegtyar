# Практика 3. Тест-кейсы по уровням пирамиды

## 0. Правило выбора уровня

| Где живёт логика                                                                     | Уровень     | Пример                                                                          |
|--------------------------------------------------------------------------------------|-------------|---------------------------------------------------------------------------------|
| в одном классе / методе, зависимости можно подменить без потери смысла               | unit        | `RoutingService`, `Card.startReservation`, порядок проверок в `AuthServiceImpl` |
| в HTTP-контракте одного сервиса: статус, тело, валидация, маппинг ошибок             | api         | `AuthControllerImpl` reason -> HTTP, `@Pan` -> 400, CMS 402/404/409             |
| в SQL, блокировках, транзакциях, брокере - мок уничтожает смысл проверки             | integration | upsert лимитов, `FOR UPDATE`, outbox -> RabbitMQ -> Notification                |
| только в полной цепочке Gateway -> … -> Logger/Notification, важной для пользователя | e2e         | жизненный цикл карты глазами клиента, кеш Gateway                               |

### 3.3 Почему пирамида получилась такой

1. По уникальным сценариям середина толще основания (≈ 38 / 59 / 3).

- Заметная часть бизнес-логики живёт не в Java, а в SQL и в протоколах.
  Дневной и месячный лимиты целиком реализованы в native-запросе
  `upsertLimitUsage`, конкурентность - в `SELECT … FOR UPDATE`, скрытие
  удалённых карт - в `@SQLRestriction`, пагинация - в Criteria API. Для
  таких кейсов (TC-A-10…12, 17, 20, TC-C-08, 10, 11, 14) unit с моком
  репозитория проверял бы мок, поэтому самый низкий адекватный уровень -
  integration.
- Плотные контракты между сервисами. Authorization интерпретирует
  HTTP-коды CMS (400/402/404/409/500/503) как бизнес-исходы, а сам отдаёт
  Switch 200/403/404/422/503/400. Ошибка в одном коде меняет ответ клиенту
  (например, 409 от reserve превращается в `96`, а не в `05`). Отсюда 15
  api-кейсов.
- Асинхронные пути и отказоустойчивость нельзя проверить моками. Outbox,
  доставка в Logger, DLQ, откат при недоступном брокере, retry к
  Authorization.

2. Если считать параметризованные строки, форма почти классическая
(65 / 33 / 2). 45 pairwise-комбинаций - это unit-тесты решения
`AuthServiceImpl` и валидации DTO.

3. E2E мало (2 кейса, ~3 %). Сквозная цепочка Gateway ->
Switch -> Authorization -> CMS -> RabbitMQ -> Logger/Notification поднимает 9
контейнеров, зависит от eventual consistency (polling до 5–10 s). 
4. В E2E оставлено только то, что нельзя увидеть ниже:
- TC-P3-16 - «склейка» всех сервисов и обоих async-потоков в одном
  пользовательском сценарии (по смыслу smoke);
- TC-P3-17 - дефект возникает только во взаимодействии кеша Gateway с
  резервом, который идёт в обход Gateway.
